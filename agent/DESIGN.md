# 智能物联 Agent 系统 — 设计文档

> 状态：设计阶段（未写代码）｜版本 v0.1｜日期 2026-08-18
> 范围：两个独立的 Agent，共享底层公共库

---

## 1. 背景与目标

现有 ESP32 SmartHome 项目（`fishgggg/-esp32-`）已经具备：多传感器采集、阈值蜂鸣告警、Web 面板（HTTP + SSE）、MQTT 上报/下行。但它有一个共同特点——**所有数据都是"全部接收后靠人提前设计的需求门槛"被动处理**，没有"判定 → 主动触达"的能力。

本设计新增两个 Agent，目的是给系统加上一层智能：

| Agent | 一句话目标 | 形态 |
|---|---|---|
| **物联网数据判定 Agent** | 监听 ESP32 数据流，判定故障/波动，主动推送报告与告警到指定人 | 常驻服务（daemon） |
| **文档总结 Agent** | 自动检索并总结技术文档/项目，落盘为本地 Markdown | 批处理工具（一次性） |

两者目的不同、形态不同，但共享同一套底层（LLM 调用、配置加载、Markdown 落盘、日志）。

---

## 2. 总体范围与非目标（MVP 边界）

### 2.1 第一版要做（MVP）

- 物联网 Agent：规则判定 + 分级告警 + Server酱通知 + 每日报告
- 文档总结 Agent：单文档/单项目 → 模板化 Markdown 总结

### 2.2 第一版明确不做

- **Agent 不自动执行控制动作**（只告警，不自动开空调/关设备）
- 云端部署（第一版纯本地局域网）
- 机器学习/时序预测模型（先上确定性规则）
- 多租户、鉴权、公网暴露
- 文档总结的 OCR / 多模态（图片、扫描件 PDF）

## 3. Agent 一：物联网数据判定 Agent

### 3.1 定位与增量价值

ESP32 继续只做「采集 + 上报 + 执行」；判定与通知移到一个独立 Python 进程。增量价值：

1. 通知对象：从「现场蜂鸣器」扩展到「远程人」（微信 / 邮件）
2. 判定：从「单点瞬时阈值」升级到「多传感器关联 + 趋势 + 时间窗聚合」
3. 报告：从「没有」到「定期自然语言日报 / 周报」
4. 规则：从「编译进固件」变为「运行时改 YAML，不改代码不重烧」

### 3.2 架构与部署（已定：本地 Python 进程 + 复用 MQTT broker）

```
ESP32 ──publish smarthome/sensor──▶ MQTT Broker ──subscribe──▶ IoT Agent（判定 + 通知）
  ◀────────── subscribe smarthome/cmd ◀───── publish 控制指令（可选，后续）
```

- **部署位置**：本地 Python 进程（PC / 树莓派），与 ESP32 同一局域网
- **MQTT Broker**：复用项目现有 `192.168.4.2:1883`，**ESP32 侧零改动**
- **数据接入**：订阅 `smarthome/sensor`，解析现有 JSON

### 3.3 数据流

```
传感器数据 ─▶ 接入层 ─▶ 规则引擎（过滤/触发）
                          │
                          ├─ 无异常 ─▶ 丢弃（只进历史缓冲）
                          │
                          └─ 触发事件 ─▶ 分级判定
                                          ├─ 硬告警 ─▶ 直接通知（不调 LLM）
                                          └─ 软分析 ─▶ 调 LLM 判定 ─▶ 生成描述 ─▶ 通知
```

### 3.4 模块拆解

| 模块 | 职责 | 关键点 |
|---|---|---|
| 数据接入层 | 订阅 `smarthome/sensor`、解析 JSON | paho-mqtt，断线重连 |
| 规则引擎 | 触发事件 + 过滤噪声 | 阈值 + 迟滞 + 时间窗 + 状态机 + 冷却去重 |
| LLM 判定层 | 软分析：故障/波动/传感器异常 + 描述 | 可选开关，只在规则触发后调用 |
| 通知层 | 发报告与告警 | 可插拔 channel 接口 |
| 状态记忆层 | 历史数据、告警历史 | SQLite（原始采样可选 CSV/环形缓冲） |
| 配置层 | 阈值、渠道、客户、冷却全外置 | YAML，改配置不改代码 |
| 观测层 | Agent 自身日志 | 结构化日志，分级 |

### 3.5 判定逻辑：分级告警 + 事件分类

**事件分类（规则引擎里明确区分）：**

| 类别 | 含义 | 例子 |
|---|---|---|
| 超限型 | 数值越过阈值 | 温度偏高、CO₂/烟雾超标 |
| 缺失型 | 数据没来本身就是故障 | 心跳包超时 → 设备离线 |
| 突变型（可后置） | 变化速率超阈值 | 温度 10s 内上升 3℃（提前预警） |

**分级告警：**

| 级别 | 触发 | 调 LLM? | 例子 | 说明 |
|---|---|---|---|---|
| **硬告警** | 纯规则，立即 | ❌ 不调 | 心跳丢失(离线)、烟雾超严重阈值 | 不依赖网络/key，保证最危险的事第一时间推出去 |
| **软分析** | 规则触发 | ✅ 调 | 温度偏高/上升趋势 → 判"故障 vs 阳光直射 vs 传感器抖动" | LLM 做精细判断 + 生成人话描述 |

**状态机（防反复横跳）：** `Normal → Warning → Critical`，恢复时回退并可选发"已恢复"通知。

**迟滞（Hysteresis）：** 触发阈值 ≠ 恢复阈值。例：温度 ≥30℃ 触发告警，回落 ≤28℃ 才恢复，避免边界抖动。

**冷却去重：** 同一告警 N 秒内不重复发；状态未变不重发。

### 3.6 通知渠道

| 落点 | 面向 | 用途 | 优先级 |
|---|---|---|---|
| Server酱（微信） | 主动触达手机 | 告警/日报推送 | ✅ 第一渠道（已定） |
| 邮件 | 运维留痕 | smtplib 发邮件 | 第二渠道 |
| Web 端 | 看板展示 | 告警描述回写面板 | 复用现有 SSE，可顺手做 |

- 报告与告警分开：**定期报告** = 汇总趋势（日/周报）；**事件告警** = 阈值触发即时通知
- 渠道抽象成可插拔接口（`send(channel, payload)`），新增渠道不碰判定逻辑

### 3.7 配置（YAML 示例结构）

```yaml
mqtt:
  broker: 192.168.4.2
  port: 1883
  topic_sensor: smarthome/sensor
  topic_cmd: smarthome/cmd

rules:
  heartbeat:
    timeout_s: 60            # 心跳超时 → 离线硬告警
  temperature:
    warning_c: 30.0
    critical_c: 35.0
    recover_hysteresis_c: 2.0
    window_s: 120            # 时间窗聚合
  co2: { ... }
  smoke: { ... }

llm:
  enabled: true              # 软分析开关
  provider: qwen             # doubao / qwen / openai / claude
  model: qwen-max

notify:
  serverchan:
    sendkey: "SCTxxxx"
  email:
    smtp_host: smtp.qq.com
    to: ["ops@example.com"]

cooldown_s: 300              # 同一告警冷却
```

### 3.8 限制与边界

- **判定精度上限 = 规则质量 + 传感器精度**（MQ-135 是"CO₂ 估算"，报告写"偏高"而非精确 ppm）
- **LLM 依赖外网 + key + 延迟 + 成本，输出不可完全复现** → 实时安全告警**绝不**交给 LLM，只走硬告警
- **LLM 只在规则触发后调用**，绝不每个采样点都调
- **通知不保证送达**（webhook/邮件可能失败）→ 失败重试 + 本地留痕
- **安全**：MQTT 明文、无认证 → 仅限可信局域网，Agent 必须同一网段
- **实时性**：秒级延迟，非工业毫秒级

## 4. Agent 二：文档总结 Agent

### 4.1 定位

输入一个「文档/项目」路径（或 URL），自动检索、切分、调用 LLM 总结，按固定模板落盘为本地 Markdown。用于项目复盘与递交。

### 4.2 实现形态演进（先 skill，后 agent）

**skill 与 agent 的本质区别**：不是"简→繁"，而是"跑在哪、谁编排"。

| | Skill（Claude Code 的 `/` 命令） | Agent（独立 Python 脚本） |
|---|---|---|
| 跑在哪 | Claude Code 里 | 独立进程 |
| 谁当大脑 | Claude Code 自己读/总结/写 | Python 直接调 LLM API |
| 开发量 | ≈ 写一个 prompt 模板 | 搭 API 调用 + 文件 IO + 切分 |
| 能否脱离环境 | 不能 | 能，可批量、可分享 |

**演进路径（推荐）：**

1. **Phase 1 — Skill**：写 `/summarize <path>`，目的是**最快验证总结模板/prompt 效果**。效果好就改 prompt，不碰基础设施。
2. **Phase 2 — Agent（Python）**：模板成熟后固化成独立脚本，直接调 LLM API。价值 = 脱离 Claude Code 也能跑、批量扫目录、给队友用。

> 原则：先用 skill 验证「总结出来长什么样」，再用 Python 固化「载体能不能独立跑」。

### 4.3 处理流水线

```
输入(路径/URL)
  → 输入解析：识别 .md / .pdf / 代码目录 / URL（PDF 转文本、目录用 tree + 只读关键文件）
  → 检索/切分：长文档按标题/长度切 chunk；目录级 = 文件清单 → 挑重点
  → 总结(map-reduce)：每 chunk 各自总结 → 二次汇总（解决超长文档塞不进 context）
  → 模板落盘：写 xxx_summary.md
  → 索引维护：批量模式生成一行一条的总索引
```

### 4.4 输出模板（固定结构）

```markdown
---
title: <项目/文档名>
type: summary
date: <日期>
source: <路径/URL>
---

## 项目定位
## 架构
## 关键参数 / 配置
## 踩过的坑 / 注意事项
## 结论与待办
```

### 4.5 限制与边界

- 总结质量上限 = LLM 本身 + 文档质量（错别字、缺上下文会带偏）
- PDF 扫描件要 OCR，纯文本 PDF 才能直接抽
- 超长文档 map-reduce **会丢跨章节关联**
- 私密/敏感文档别传云端 LLM（需本地模型或脱敏）
- 目录级是"采样"，不可能逐行读完几万行代码，结论需标注"基于采样"

---

## 5. 共性：可复用底层

两个 Agent 共享一个公共小库：

- **LLM 调用封装**：provider 切换（doubao/qwen/openai/claude）、重试、超时、成本统计
- **配置加载**：统一 YAML 解析
- **Markdown 落盘 + 索引**：模板写入、索引追加
- **结构化日志**：统一日志格式

上层各管各的，底层复用。
